# Release compatibility checklist

Apply this release rule across the user's legacy Thunderbird add-ons, including QuickFolders, quickFilters, FiltaQuilla, and SmartTemplates:

- Release notes (`release-notes.html` and `release-notes.md`) describe the completed release. Do not add "work in progress", "WIP", or equivalent labels unless the user explicitly requests them. This is independent of retaining `preXX` during testing and accurately labeling publication status in `version.html`.
- For ATN publishing in `release-notes.html`, use `<tt>` for monospace text, not `<code>`. This corrects the earlier tag whitelist: allow `<tt>` and exclude `<code>`. Validate the remaining ATN tag restrictions as before. Markdown release notes may continue to use backticks.
- Keep detailed release notes technically informative: explain the cause, relevant Thunderbird API removals or changes, the implemented replacement, and affected behavior where useful. Reserve aggressive simplification for the in-app `whats-new-list`, where screen space and reader attention are limited; do not copy its abbreviated wording into detailed release notes at the expense of the reasoning.
- Before each release, check https://addons.thunderbird.net/en-US/thunderbird/pages/appversions/ for the highest major Thunderbird version accepted by ATN.
- Set `applications.gecko.strict_max_version` in `manifest.json` to that major version followed by `.*`. Do not use only the current stable version or an unrestricted wildcard. This reduces releases needed solely to advance the compatibility ceiling for legacy add-ons.
- Across all of the user's add-ons, proactively support upcoming Thunderbird versions as aggressively as practical. User-facing wording such as "is now compatible with Thunderbird N" is acceptable reassuring shorthand for this forward compatibility support, including while N is in beta; do not automatically replace it with caveats or treat it as a claim of exhaustive testing. Keep the Thunderbird version addressed by a specific fix independent of the manifest compatibility ceiling (for example, issue #720 addresses Thunderbird 159 while `strict_max_version` is `160.*`). Preserve the user's chosen wording and address regressions as they emerge.
- Check https://whattrainisitnow.com/calendar/ for upcoming release dates when planning compatibility fixes and release timing. ATN's accepted application versions determine the manifest ceiling; the calendar informs scheduling.
- Experimental add-ons require manual ATN review. Plan submission preferably 10 days before the relevant Thunderbird release, with one week as the normal minimum lead time. These are planning buffers, not guaranteed review times; flag a shorter window when assessing release readiness.
- If the live ATN version list cannot be read, report that limitation rather than claiming the highest accepted version was verified.
- Keep the `preXX` suffix during preparation and testing; remove it only when the release is fully ready, immediately before the final release commits.
